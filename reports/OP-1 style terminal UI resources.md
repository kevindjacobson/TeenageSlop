# Nobody has skinned Claude Code as an OP-1; the parts exist

No Claude Code mod, plugin, status line or terminal project reproduces the Teenage Engineering OP-1 display, so the `op1-crew` pane would be first of its kind — but every ingredient it needs already exists and is legally clean. The OP-1 look reduces to a short rule set (black ground, four encoder colours plus one dim grey, thin anti-aliased strokes, one line-art figure per screen, huge light numerals, tiny-caps labels, boxed chips, needle gauges and segmented ladders) and a community-read firmware palette (**#4D9EFF / #00ED95 / #FFFFFF / #FF3A5D on #000000, dim #6F7173**) ([popcorp, op-forums #1373](https://op-forums.com/t/custom-firmware-on-the-op-1/4283/1373)). Because the target terminal is Ghostty, the mod should draw the screen as a real picture: Claude Code's mods API has an `Image` element that accepts raw RGBA bytes and draws as a picture in kitty 0.28+, Ghostty and iTerm2 3.5+ ([mods gallery](https://code.claude.com/docs/en/plugins/mods/gallery.md)), which means the pane can render genuine OP-1-style vector line art in-module, with a quadrant-glyph `Raster` fallback for tmux and an `Svg` fallback for the desktop app. The event plumbing is already proven by native mods such as claude-flightdeck (`agent.spawn`, `tool.call`, `turn.*`, `$.state` reducers) and agenten-monitor (task progress derived from `TodoWrite`/`TaskCreate`/`TaskUpdate` calls) ([scasella/claude-flightdeck](https://github.com/scasella/claude-flightdeck); [Julianspk/agenten-monitor](https://github.com/Julianspk/agenten-monitor)). The two things worth building from scratch are a small original stroke font and the agent figures as polylines, because the OP-1's own font and art are proprietary and the CC0 pixel-sprite packs are the wrong idiom (pixel art, not anti-aliased line art) for a pixel-rendered pane. Copy stays in Claude Code vocabulary throughout: TURN, CTX, READ/EDIT/SHELL/AGENT, TASKS, model and permission-mode chips, and a NEEDS YOU line.

## The OP-1 look is seven rules, one palette, and no reusable art

The design language is far more codified than the scarcity of official TE statements suggests. TE itself says only that colour is the link between encoder and graphic ("A green graphical element or text hints that the green encoder will change its value or position") and that the hardware colours were chosen "to keep things playful" ([teenage.engineering layout guide](https://teenage.engineering/guides/op-1/original/layout); [OP-1 field guide PDF](https://assets.teenage.engineering/_img/69f248938d433104c4dd1846_original.pdf)). The rest comes from people who patch the firmware. The stock palette read from the firmware SVGs by op1r's author is **Blue #4D9EFF, Green #00ED95, White #FFFFFF, Red #FF3A5D, Grey #6F7173, Lilac #DFD9FF, Pale #AEB1DC on black, with no opacity support** — "for dim states, use darker versions of the same colours" ([popcorp #1373](https://op-forums.com/t/custom-firmware-on-the-op-1/4283/1373)). SquareWave Studio's op1-design-kit publishes an independent token set (#698EFF / #00ED95 / #FFFFFF / #FF423F, secondary #B9B9C9, decorative #625D77) and is honest that these are "consistent preview tokens, not calibrated OLED colours" ([op1-ui.json](https://github.com/squarewave-studio/op1-design-kit/blob/main/op1-ui/tokens/op1-ui.json)). The green agrees across both sources; the user's screenshots show a blue closer to the kit's more violet #698EFF, which is consistent with OLED and camera drift, so either set is defensible and the "orange" must be a red-orange coral, never a yellow-orange.

Geometry is equally well measured. The canvas is **320 × 160 logical units** (iFixit confirms a 320 × 160 AMOLED at 60 fps) with content kept above about y = 140 because the lower edge is unreliable on-device; community layout practice is an 8-unit grid with an 8/8/16/8 safe zone ([iFixit](https://www.ifixit.com/Device/Teenage_Engineering_OP-1); [maxaw #1371](https://op-forums.com/t/custom-firmware-on-the-op-1/4283/1371)). Type sizes measured from stock SVG templates are 13.33 units for browser rows, **20 for parameter values, 40–43 for clock/BPM, and 53.34 for the mixer level numerals**, all at a 1.5-unit stroke (2 for the clock) ([op1-ui.json](https://github.com/squarewave-studio/op1-design-kit/blob/main/op1-ui/tokens/op1-ui.json)). Encoder lanes sit at x = 9/89/169/249 with a right anchor at 311, in fixed left-to-right order blue, green, white, orange ([DESIGN.md](https://github.com/squarewave-studio/op1-design-kit/blob/main/op1-ui/docs/DESIGN.md)). Both user screenshots confirm the composition rules: pure black; exactly four hues plus a dim grey-violet for grids and inactive ticks; one dominant illustration per screen (boxer, cow, exploded telephone, radar square, isometric grid plate, reels); labels in tiny caps in their lane colour with values two to four times larger in the same colour; secondary state as small boxed chips ("MAX EQ", "CLEAN", "SIDEBAND", "FX", "Z FDB"); continuous amounts as needle gauges with tick arcs or as vertical segmented ladders; and dashed baselines under curves. Reviewers' observations round this out: the display "uses colour and animation meaningfully" and motion is reserved for things that explain the mechanism — reels spin with transport and settle with "light physics", mixer needles follow level, the Finger figures play on key taps ([Sound On Sound](https://www.soundonsound.com/reviews/teenage-engineering-op1); [CDM 2010](https://cdm.link/2010/01/17/teenage-engineerings-op-1-instrument-hands-on-videos-why-its-different/)).

The hard boundary is reuse. The firmware's UI is demonstrably SVG: an unpacked `.op1` yields `content/display/*.svg`, one per screen, plus `opfont.svg` (an uppercase-only monoline stroke font that doubles as the icon set) and `colors.svg` ([op1hacks/docs](https://github.com/op1hacks/docs)). Everything in it is TE's copyright, and every community project refuses to redistribute it: op1-design-kit's CI forbids committing `opfont.svg`, `kerntable.db` or `colors.svg`, and its licence says "MIT grants no rights to stock assets" ([FONTS.md](https://github.com/squarewave-studio/op1-design-kit/blob/main/op1-ui/docs/FONTS.md); [SOURCES.md](https://github.com/squarewave-studio/op1-design-kit/blob/main/op1-ui/docs/SOURCES.md)). No Figma, Dribbble, Lospec or browser emulator of the screens exists. So the mod must draw original art in the idiom — which the on-device constraints make easy to imitate faithfully, because the OP-1 renderer itself only handles lines, polylines, circles, polygons and `matrix` transforms, with butt caps, a budget of roughly 150 lines per frame, and dots drawn as two short crossing lines because tiny circles do not render ([svg.md](https://github.com/op1hacks/docs/blob/master/svg.md); [popcorp #1373](https://op-forums.com/t/custom-firmware-on-the-op-1/4283/1373)). A rasterizer that supports exactly that vocabulary will look right by construction.

## Ghostty's kitty protocol makes real pixels the primary renderer

Every shipped pixel-art mod to date chose block glyphs over the `Image` element because `Image` degrades to alt text in tmux and on terminals without a graphics protocol ([besanek/claude-nyan-cat](https://github.com/besanek/claude-nyan-cat); [whirlwin/claude-code-halloween](https://github.com/whirlwin/claude-code-halloween)). That trade-off inverts for a Ghostty user. The mods reference says `Image` takes "PNG or RGBA bytes up to 2 MiB, or a file path, `columns` and `rows` up to 255, and `alt` text" and draws as a picture in kitty 0.28+, Ghostty and iTerm2 3.5+ ([gallery.md](https://code.claude.com/docs/en/plugins/mods/gallery.md)). An OP-1 screen is anti-aliased 1.5-unit strokes on black at 320 × 160; no character-cell technique reproduces that, whereas an in-module RGBA buffer reproduces it exactly. The recommendation is therefore a three-tier renderer driven by one scene model: **tier 1, `Image` with RGBA bytes rendered in-module** (Ghostty, kitty, iTerm2); **tier 2, a keyed quadrant-glyph `Raster`** for tmux and other terminals; **tier 3, `Svg`** for the desktop app, where `Raster` is unavailable and which, pleasingly, is the OP-1's native format anyway ([interface.md](https://code.claude.com/docs/en/plugins/mods/interface.md)). Because the scene is a list of coloured polylines, circles and glyph strokes, the same data emits all three outputs; only the back end changes.

Two practical constraints shape the pixel path. First, animation. `$.ui.blit` repaints only a keyed `Raster` in place; full redraws via `$.ui.invalidate('ui.render')` are "throttled to 10 a second, or 30 in the terminal for the visible pane" ([reference.md](https://code.claude.com/docs/en/plugins/mods/reference.md)). The notes contain no evidence that `Image` can be blitted, so the pixel tier animates by re-rendering the whole pane tree at a modest clock — which is fine for OP-1-style motion, where needles ease, numerals tick and figures alternate between two or three poses. Copilot CLI's engineers settled on 75 ms (~13 fps) for their terminal animation and noted higher rates flicker in some terminals; the halloween Clawd mod uses 150 ms and ruvnet's field guide 80 ms ([GitHub Blog](https://github.blog/engineering/from-pixels-to-characters-the-engineering-behind-github-copilot-clis-animated-ascii-banner/); [ruvnet gist](https://gist.github.com/ruvnet/a485e930b148185197fc53fd38b429ea)). A 100–125 ms tick with a critically damped spring for needle and ladder motion (the harmonica pattern: fixed FPS, `Update(pos, vel, target)` per tick, damping = 1 for no overshoot) will read as "OP-1 light physics" without exceeding the throttle ([charmbracelet/harmonica](https://github.com/charmbracelet/harmonica)). Keep the rasterizer cheap by honouring the OP-1's own budget of roughly 150 strokes per frame. What remains uncertain is the cost of pushing a fresh RGBA buffer through the kitty protocol ten times a second and whether Claude Code scales the image to the `columns × rows` cell box or crops it; neither is documented in the notes, so the first spike should measure both and keep the buffer small (an integer multiple of 320 × 160 such as 640 × 320 is 800 KiB of RGBA, well under the 2 MiB cap).

Second, pane geometry. A pane is "a sidebar beside the transcript in a wide fullscreen terminal, or a framed region above the prompt otherwise"; `$.ui.open` accepts `rows` and `columns` at most 45% of terminal width, and a mod-opened pane only appears at ≥144 columns (110 once the user has opened it themselves) ([interface.md](https://code.claude.com/docs/en/plugins/mods/interface.md)). Since terminal cells are roughly 1:2, an 80-column by 20-row image region is a 2:1 box that matches the 320 × 160 canvas; a 64 × 16 region does the same at 45% of a 144-column terminal. Design the scene in 320 × 160 logical units exactly as the firmware does, keep critical content above y = 140, and scale at render time.

For the `Raster` fallback, the notes give a complete recipe. A `Raster` packs every cell as code point, fg and bg as 24-bit hex in a base64 `Uint32Array`, up to 512 × 256 cells, and "rounds each color to a smaller palette, so `0x2e7d32` draws as `#337733`" — the OP-1's flat five-colour scheme survives that quantisation far better than gradients would ([interface.md](https://code.claude.com/docs/en/plugins/mods/interface.md)). Quadrant blocks (U+2596–259D, all East-Asian-Width Neutral) give 2 × 2 pixels per cell with no visible gaps; half-blocks give 1 × 2 with two colours; braille gives 2 × 4 but a single colour per cell ([Ratatui Marker docs](https://docs.rs/ratatui/latest/ratatui/symbols/enum.Marker.html)). Text in this tier should use `Text` elements in uppercase with lane colours, and large values as FIGlet-style block numerals, mimicking the 53-unit mixer digits. Avoid anything East-Asian-Wide (⬛ ⏩) and never emit U+FE0F, which Kitty counts as two cells while Alacritty ignores it ([zsh-workers 2024](https://www.zsh.org/mla/workers/2024/msg00487.html); [wcwidth docs](https://wcwidth.readthedocs.io/en/latest/api.html)).

## Event plumbing is solved; borrow flightdeck's reducer split

The mod API surface relevant here is settled and publicly exercised. A mod is a plugin whose `hooks/hooks.json` lists `"modules": ["./register.js"]`; the module exports `register(on)` and subscribes with `on('ui.render', { component: 'Pane' }, ...)`, resolving `Box/Text/Button/Input/Select/Raster/Image/Client/Svg` from `$.ui.resolve(e)` ([reference.md](https://code.claude.com/docs/en/plugins/mods/reference.md)). The data feeds map one-to-one onto the user's required readouts: `turn.start`/`turn.step`/`turn.complete` drive the turn timer; `tool.call` and `tool.check` (with `e.agentId` for subagent calls since v2.1.290) feed the READ/EDIT/SHELL/AGENT counters and per-figure activity; `agent.spawn` plus `$.agent.list()` (statuses `pending`/`running`/`waiting`/`idle`/`completed`/`failed`/`killed`) populate the subagent figures; `$.session.usage()` returns `{ startedAt, context, rateLimits, cost }` for the context gauge; `session.compact` resets it; and `classic.<Event>` exposes every settings hook, so `classic.PermissionRequest` and the `AskUserQuestion` render site are the sources for the NEEDS YOU line ([reference.md](https://code.claude.com/docs/en/plugins/mods/reference.md)). Tasks have no dedicated event; agenten-monitor's precedence order is the practical answer — read `TodoWrite`, `TaskCreate` and `TaskUpdate` tool calls and fall back to a per-agent-type median duration from recent runs ([Julianspk/agenten-monitor](https://github.com/Julianspk/agenten-monitor)).

Structurally, claude-flightdeck is the template: pure reducers in `hooks/core.ts`, rendering in `hooks/register.tsx`, state in `$.state` atoms, 24 tests, no network and no model calls, with subagent cards carrying task, type, tokens, steps and a running clock plus a main-model panel with a context gauge and compaction count ([scasella/claude-flightdeck](https://github.com/scasella/claude-flightdeck)). The OP-1 pane is essentially flightdeck's data model with a different painter. Persist user settings (render tier, figure style, sound on/off) in `$.store`, which is 4 MiB per plugin shared across sessions, and stop every `$.clock.every` timer on `ui.close` and `session.end` ([dev.to pane tutorial](https://dev.to/nakadadev/how-to-add-a-side-pane-to-claude-code-with-a-mod-using-uiopen-and-uirender-3c24); [ruvnet gist](https://gist.github.com/ruvnet/a485e930b148185197fc53fd38b429ea)). Note the API's sharp edges: `focus`, `closeOnEscape` and `holdToasts` accept only `true` (passing `false` throws), and a mod cannot bind Tab or the arrow keys, so any pane controls should be single-letter hotkeys on `Button` elements.

For "agents as little figures", the field is wide open inside the Claude Code TUI. The mature crew visualisers are browser canvases — pixel-agents at ~9.8k stars, claude-office, backstage, codemap — and the only in-terminal one, pixtuoid, is a separate Rust process that already prefers "terminal images (kitty, SIXEL, iTerm2) where supported, and otherwise half-block cells", which validates the tiered approach ([pixel-agents-hq/pixel-agents](https://github.com/pixel-agents-hq/pixel-agents); [pixtuoid/pixtuoid](https://github.com/pixtuoid/pixtuoid)). No mod draws multiple subagents as distinct sprites inside a pane; agent-theater animates only the main agent, and flightdeck, overseer and mission-control draw cards or lines ([afu-it/agent-theater](https://github.com/afu-it/agent-theater)). Two state vocabularies are worth copying wholesale: claude-code-mascot-statusline's nine hook-driven states (idle, thinking, tool running, tool success, tool failure, permission prompt, subagent running, done, auth success) and petdex's sprite-sheet rows (idle, running, waiting, failed, review, waving), both of which map cleanly onto `$.agent.list()` statuses ([TeXmeijin/claude-code-mascot-statusline](https://github.com/TeXmeijin/claude-code-mascot-statusline); [crafter-station/petdex](https://github.com/crafter-station/petdex)).

## Draw the figures and font yourself; buy nothing but sounds

The asset research points firmly away from the CC0 sprite packs for the primary tier. Kenney Micro Roguelike (8 × 8), Tiny Dungeon (16 × 16), the OGA 8x8 Character Pack and DarkOnes are all CC0 and would convert to an 8 × 4 half-block "guy" in seconds — but they are pixel art, and the OP-1 is anti-aliased vector line art; the notes themselves warn that heavy pixel faces belong to the Pocket Operator and EP-133 segment displays, not the OP-1's 60 fps OLED ([Kenney Micro Roguelike](https://kenney.nl/assets/micro-roguelike); [OGA 8x8 Character Pack](https://opengameart.org/content/8x8-character-pack)). None of the CC0 packs ships "working" or "cheer" frames at 8 × 8 anyway; DarkOnes' "Pushing" and "Use" are the nearest donors ([itch DarkOnes](https://the-lazy-sorcerer-arts.itch.io/platformer-characther)). The better plan is figures in the Finger-sequencer and Punch idiom — a line-art body of twenty to forty strokes with a head circle, drawn as polylines in 320 × 160 units — with poses per status: running (hands on a keyboard, two alternating frames at ~150 ms), waiting (one arm up, a small "?" chip), idle (arms down), completed (both arms up for a few ticks, then idle), failed or killed (slumped, outlined in red-orange). The lead agent is drawn larger and centred; subagents are smaller and sit in a row beneath, each with its model chip and running clock, which echoes the Finger sequencer's two players and the Mixer's "four repeated lanes" ([teenage.engineering sequencers](https://teenage.engineering/guides/op-1/original/sequencers); [STOCK.md](https://github.com/squarewave-studio/op1-design-kit/blob/main/op1-ui/docs/STOCK.md)). Reserve the CC0 pixel sprites for the `Raster` fallback tier, where everything is a bitmap and the mascot-statusline `pack.yaml` format is the only documented, user-editable half-block sprite schema found.

The font follows the same logic. The OP-1 typeface is an unnamed, unreleased stroke font; the closest free stand-in is Iosevka Thin/ExtraLight/Light (OFL), chosen by op1-design-kit for previews with weight tied to size (XS 400 down to XL 100), and the kit's spacing heuristic for stock glyphs is "minimum narrow-glyph advance of 0.22h, inter-letter gap of 0.17h and space advance of 0.48h" where h is cap height ([FONTS.md](https://github.com/squarewave-studio/op1-design-kit/blob/main/op1-ui/docs/FONTS.md)). A mod that renders RGBA in-module has no TTF rasterizer, so author a small original stroke font — A–Z, 0–9 and a dozen punctuation marks as polylines on a 320 × 160-unit grid, rendered at 1.5-unit stroke with butt caps — exactly the mechanism `opfont.svg` uses, without copying its shapes. The reference screenshots show what to aim for: condensed geometric caps with rounded corners, an open-topped "4", a flat-topped "5", a narrow oval "0". Pixel fonts such as Departure Mono, Silkscreen or Tom Thumb only matter for the fallback tier or if the user wants to rasterise 3 × 5 labels into block cells ([rektdeckard/departure-mono](https://github.com/rektdeckard/departure-mono)).

Sound is the one place to take assets off the shelf. `$.audio.play` exists in the mods API, and Kenney's CC0 UI Audio (50 files), Interface Sounds (100 OGG files) and Digital Audio (60 files) cover clicks, confirms and square-wave beeps; the Godot repackagings supply WAV if OGG playback is awkward ([Kenney UI Audio](https://kenney.nl/assets/ui-audio); [Kenney Interface Sounds](https://kenney.nl/assets/interface-sounds); [Godot asset 795](https://godotengine.org/asset-library/asset/795)). Map a short Digital Audio blip to agent spawn and completion, a Lokif CC0 error tone to failures, and a two-note Interface Sounds confirm to NEEDS YOU — off by default, toggled from the pane. Skip the freesound cassette clicks: they are tape vocabulary, and the skin-not-metaphor rule applies to audio as much as labels.

## Module map in Claude Code vocabulary

The constraint that the OP-1 is a skin, not a metaphor, is easiest to hold if each OP-1 visual idiom is bound once to a Claude Code concept and never relabelled. The table below is that binding; the left column is the visual device, the right column is the only copy allowed on it.

| OP-1 visual idiom (from screenshots and notes) | Claude Code module and copy | Lane colour | Data source |
|---|---|---|---|
| Tape-style counter numerals ("2:50:20") and boxed digit | **TURN** timer as 40-unit numerals; boxed turn number | Blue | `turn.start` / `turn.complete`, `$.clock` |
| Needle gauge with tick arc; big value | **CTX** context fill, needle plus 53-unit "%" numeral; turns red-orange past a threshold | Green | `$.session.usage().context`, `session.compact` |
| Mixer's four huge numerals "02 34 45 23" | **READ EDIT SHELL AGENT** counts for the current turn | White (labels in lane colours) | `tool.call` grouped by tool name |
| Boxed chips ("MAX EQ", "CLEAN", "SIDEBAND") | **MODEL** chip (e.g. OPUS), **MODE** chip (ASK / AUTO / PLAN), branch chip | Red-orange chip for mode when it is permissive | `session.*`, `SessionMode` site |
| One large line-art figure (boxer, keyboard players) | **LEAD** agent figure, posed by status | White | `turn.*`, `tool.call` without `agentId` |
| Finger's two smaller players; mixer's repeated lanes | **AGENTS** row: one small figure per subagent with clock and model chip | Figure in lane colour, by spawn order | `agent.spawn`, `$.agent.list()`, `tool.check` with `agentId` |
| Segmented vertical ladder; checkered pattern rows | **TASKS** ladder with filled segments and "3/7" | Green | `TodoWrite` / `TaskCreate` / `TaskUpdate` tool calls |
| Red arrow to a boxed chip ("→ MAX EQ") | **NEEDS YOU** line with the reason (permission, question) | Red-orange, blinking at ~2 Hz | `classic.PermissionRequest`, `AskUserQuestion`, agent `waiting` |
| Dim grey grid, dashed baselines, tick marks | Layout scaffolding only, never labelled | #6F7173 | — |

Words that must not appear anywhere in the pane, per the user's rule: tracks, REC, tape, mixer, reels, BPM, FX. The OP-1 idioms that carry those words (reels, "TO REC", the tape head) are the ones to leave out; needle gauges, ladders, chips, numerals and figures carry no musical meaning and are safe.

The implementation sequence that follows from all of this is short. Start with the scene model and the three painters (RGBA, Raster, Svg) against a static mock state, and measure Ghostty's behaviour with a 640 × 320 RGBA `Image` re-rendered at 8–10 fps before committing to it. Then port flightdeck's reducer structure for the eight feeds above, add the stroke font and figure poses, and only then add motion: springs on the CTX needle and TASKS ladder, two-frame typing for running figures, a 2 Hz blink for NEEDS YOU. Pin all referenced mods to commits, since the catalogue at mods.aidojo.si counted 5,898 mods scanned the day before this research and the ecosystem churns daily ([karanb192/awesome-claude-code-mods](https://github.com/karanb192/awesome-claude-code-mods)).

## Conclusion

The most useful discovery is that the OP-1's own rendering constraints are a gift to a terminal implementer: a renderer limited to lines, polylines, circles, matrix transforms, butt caps and about 150 strokes per frame, with a stroke font drawn in the same pen, is trivial to build in a few hundred lines of TypeScript and produces the look by construction — without touching a single TE asset. Ghostty turns that from a character-cell approximation into the real thing, and the same polyline scene degrades gracefully to quadrant glyphs and to SVG, so the pixel path costs nothing in portability.

The second shift is in where the novelty lies. The data layer is a solved problem with public templates; the font and figures are a day of drawing; the genuinely open design work is the vocabulary binding — deciding once which OP-1 device shows which Claude Code quantity, and policing the labels. That binding, not the rasterizer, is what will make the pane read as "Claude Code in an OP-1 skin" rather than "a synth that happens to show agents".
